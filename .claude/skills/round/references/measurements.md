# Round 실측값

`round` 스킬의 Codex 호출 관찰값이다. 규칙은 [../SKILL.md](../SKILL.md)에 있고 이 문서는 근거만 담는다.

**이 저장소의 값만 적는다.** 원본 저장소 `healthviewer-demo-api`와 `healthviewer`에도 같은 이름의 문서가 있고 훨씬 큰 숫자가 있지만, 그 값을 이 저장소의 값으로 보고하지 않는다. 대상 코드베이스가 다르다.

`cached`는 `cached_input_tokens`다. CLI 경로에서는 `turn.completed`의 `usage`에 있다. **input만 보고 비용을 추정하지 않는다.** 캐시 히트가 50~90%까지 나오므로 input만 읽으면 실비를 크게 과대평가한다.

**MCP 경로로 돈 호출은 여기 적지 않는다.** tool 결과에 `threadId`와 `content`만 담겨 토큰을 관측할 수 없다. 그 라운드의 closeout은 `측정 불가`로 쓴다.

## 참고로 삼되 그대로 쓰지 않을 것

원본 저장소 `healthviewer-demo-api` 실측에서 얻은 경향이다. **숫자를 이 저장소의 값으로 옮겨 적지 않는다.** 경향만 예상에 넣는다.

- 리뷰 1회가 input 11만~57만 토큰 대역이었다. 전부 마크다운과 설정 파일이 대상이었고 `src/**` 코드 리뷰 관찰값은 없었다.
- **재검토가 첫 리뷰보다 비싸다.** 같은 범위를 다시 본 라운드 2가 라운드 1의 2.3배였다(244,477 → 569,519). 이전 라운드 findings와 수정 내역을 프롬프트에 실어야 하고, Codex가 반영 여부를 확인하려고 파일을 더 넓게 다시 읽기 때문으로 보인다. **라운드를 늘리는 비용은 선형이 아니다.** 이 저장소가 상한을 2로 줄인 실질 근거가 이것이다.
- **커밋 계획이 리뷰보다 싸지 않다.** 두 대역이 겹친다. 계획 호출을 "가벼운 마무리"로 보지 않는다.
- input이 프롬프트 길이와 비례하지 않는다. Codex가 저장소를 직접 읽기 때문이다. 프롬프트를 줄여 비용을 줄이려는 시도는 효과가 작다.

## 관찰 방법

CLI 경로 JSONL에서 뽑는다. stdout raw text를 파싱하지 않는다.

```text
{"type":"turn.completed","usage":{"input_tokens":...,"cached_input_tokens":...,"output_tokens":...,"reasoning_output_tokens":...}}
```

새 행을 추가할 때 기존 행을 지우지 않는다. 대상 규모가 다른 값을 한 줄로 합치지 않는다.
